# camera_speed_test

Прошивка для **Arduino Nano** (PlatformIO) — прибор для измерения задержки **glass‑to‑glass** в видеотракте «камера → транспорт (аналог / Ethernet / Wi‑Fi / RF) → монитор оператора». Стимул — биколорный LED, переключающийся между **красным** и **синим** (без полной темноты, чтобы автоэкспозиция камеры не «охотилась»). Фотоприёмник прижат к экрану монитора в светоизолирующей бленде. Экран прибора — **SSD1306 128×64** по I2C. Распайка — [`pins.md`](pins.md).

## Сборка и прошивка

```bash
pio run -t upload
```

При необходимости укажите порт в [`platformio.ini`](platformio.ini) (`upload_port`).

## Стек

- **MCU:** ATmega328P (Arduino Nano)
- **Дисплей:** SSD1306 128×64 (I2C, `A4`/`A5`, адрес по умолчанию `0x3C` — см. `cfg::kOledI2cAddress7bit` в [`include/Config.h`](include/Config.h)). Шрифт по умолчанию 5×8 → ≈21 знак × 8 строк. **Не обязателен** — прибор полностью управляется и читается через Serial (см. ниже).
- **Serial-консоль:** `115200 8N1`, односимвольные команды (`m` / `c` / `r` / `h`), все экраны дублируются строками с префиксами `[MENU]`, `[CAL]`, `[RESULT]` и т. п. Подробнее — раздел «Управление и наблюдение через Serial».
- **Все рабочие параметры:** [`include/Config.h`](include/Config.h)

## Управление

| Жест | Действие из главного меню |
|------|---------------------------|
| Короткое одиночное | Выход из режима / обновление главного меню |
| Двойное короткое | Явная калибровка R / B (2 фазы × `kCalibPhaseDurationMs`) |
| Долгое удержание (≥ 3 с) | Авто‑прогрев и измерение задержки (`kLatencySessionMs`) |

Из любого экрана короткое одиночное возвращает в главное меню.

### Управление и наблюдение через Serial

Прибор полностью работоспособен и **без OLED** — все экраны дублируются в `Serial` (`115200 8N1`), а кнопка целиком заменяется однобуквенными командами. Можно даже физически не подключать дисплей.

Команды (нечувствительны к регистру, по одному символу, лишние пробелы/`\r`/`\n` игнорируются):

| Символ | Эквивалент жеста | Действие |
|---|---|---|
| `m` | Single | Возврат в главное меню / выход из любого режима |
| `c` | DoubleShort | Запуск явной калибровки R/B |
| `r` | LongHold | Запуск авто‑прогрева и измерения 15 с |
| `h` или `?` | — | Печать справки |

Жесты с **кнопки** и команды из **Serial** работают параллельно; что приходит первым в данном тике `loop()`, то и обрабатывается.

После старта в Serial выводится баннер и справка:

```
=== KRAN glass2glass: boot ===

--- KRAN glass2glass: serial console ---
commands (one char, case-insensitive):
  m  - menu / back / exit any screen
  c  - CALIBRATION (R/B, 2 phases x 5s)
  r  - RUN measurement (warmup + 15s R<->B)
  h  - this help
---
```

Каждый экран мирорируется одной строкой с префиксом в квадратных скобках:

```
[MENU]  m=back  c=cal(2ph x 5s)  r=run(22s, max~500ms)  h=help
[CAL] phase=1/2 RED  avg=812 mn=810 mx=814 sprd=4 n=320
[CAL] phase=2/2 BLUE avg=210 mn=208 mx=213 sprd=5 n=320

[CAL_RESULT] R=812 +/-4  B=210 +/-5  dRB=-602  status=OK
[WARMUP] phase=1/2  LED=RED
[WARMUP] phase=2/2  LED=BLUE
[LAT] t=0.3/22.5  n=0 lost=0  min=0.0 avg=0.0 max=0.0  RB=0.0 BR=0.0
[LAT] t=1.0/22.5  n=1 lost=0  min=42.3 avg=42.3 max=42.3  RB=42.3 BR=0.0
...
[LAT] t=22.5/22.5 n=28 lost=2  min=12.4 avg=42.7 max=78.1  RB=41.5 BR=43.9

[RESULT] GLASS->GLASS, ms:
  min  = 12.40
  avg  = 42.70
  max  = 78.10
  RB av= 41.50
  BR av= 43.10
  n    = 28
  lost = 2
```

Префиксы `[MENU]`, `[CAL]`, `[CAL_RESULT]`, `[WARMUP]`, `[LAT]`, `[RESULT]`, `[ABORT]` удобно фильтровать в логах (`grep`/`Select-String`) или парсить простыми скриптами для протоколов испытаний.

В случае отказа от измерения:

```
[ABORT] reason=dRB low  R=512  B=528  dRB=16
```

Команды, введённые пользователем, эхо‑печатаются префиксом `>>`:

```
>> [cmd] CALIBRATION
```

Так в логе виден и инициатор события, и его результат.

## Принцип измерения

1. **Сканер 2 фаз** (общий для калибровки и прогрева):
   - **RED** — LED красный, измеряется уровень `cR`.
   - **BLUE** — LED синий, измеряется уровень `cB`.

   Фоновая засветка отдельной фазой **не измеряется**: LED никогда не выключается во время сессии, а влияние фона на цветовые уровни автоматически вылавливается двумя проверками пригодности ниже.

2. **Расчёт порогов** между уровнями цветов:
   - `mid = (cR + cB) / 2`
   - `tLow = mid − H`, `tHigh = mid + H` (`H = cfg::kLatencyThresholdHysteresisAdc`)
   - `dirSign = sign(cB − cR)` — на какой «стороне» порога ожидать каждое переключение.

3. **Проверка пригодности** перед измерением:
   - `|cR − cB| ≥ kFeasibleMinSpreadAdc` — иначе `dRB low` (цвета неразличимы; косвенно покрывает и случай «фон затопил оба уровня»).
   - `cR` и `cB` не в насыщении АЦП — иначе `ADC clip` (подкрутить подтяжку датчика / яркость монитора).
   - При отказе выводится экран **ABORT** с причиной и значениями уровней.

4. **Измерение R↔B** (`kLatencySessionMs`): LED переключается красный ↔ синий каждые `kLatencyBlinkHalfPeriodMs`. В момент команды на смену цвета фиксируется `t0 = micros()`; затем ожидается, что АЦП фотоприёмника пересечёт `mid` в нужную сторону (с гистерезисом). По первому пересечению — фиксируется `Δt`.

5. **Двусторонняя статистика**: задержки **R→B** и **B→R** учитываются раздельно (асимметрия Bayer/ISP/панели даёт разные значения).

## Пределы измерения и подбор параметров

Прибор измеряет задержку, ограниченную сверху **полупериодом стимула** и **таймаутом датчика**. Эти параметры выводятся из одной константы `cfg::kLatencyMaxExpectedMs` (мс):

```
kLatencyBlinkHalfPeriodMs = 1.5 × kLatencyMaxExpectedMs   // полупериод стимула
kLatencySensorTimeoutUs   = 1.2 × kLatencyMaxExpectedMs   // таймаут датчика на фронт
kLatencySessionMs         = max(15 с, 30 × полупериод)    // длительность сессии
```

Правило простое: **`kLatencyMaxExpectedMs` должен быть не меньше реальной задержки тракта**, иначе прибор начнёт либо терять выборки (если задержка больше таймаута), либо принимать «не свои» фронты (если задержка больше полупериода) → результат станет недостоверным.

### Готовые пресеты

Достаточно поменять одну строку в `include/Config.h`:

| Сценарий | `kLatencyMaxExpectedMs` | Полупериод | Таймаут | Сессия | Замечание |
|---|---|---|---|---|---|
| HDMI / низкозадержный аналог | `150` | 225 мс | 180 мс | 15 с | ~66 переключений |
| OpenIPC RTSP UDP локально | `300` | 450 мс | 360 мс | 15 с | ~33 переключения |
| **IP / RTSP / Wi‑Fi (по умолчанию)** | `500` | 750 мс | 600 мс | **22.5 с** | ~30 переключений |
| Wi‑Fi с большой буферизацией | `1000` | 1500 мс | 1200 мс | **45 с** | ~30 переключений |
| Экстремум (плохой WAN, много буферов) | `2000` | 3000 мс | 2400 мс | **90 с** | ~30 переключений |

### Что произойдёт, если задержка превысит `kLatencyMaxExpectedMs`

| Реальная задержка | Что увидите |
|---|---|
| ≤ `1.2 × max` | Норма, выборки захватываются |
| между `1.2 × max` и `1.5 × max` | Все или почти все выборки уходят в **`lost`**, финал с маленьким `n` или нулевым |
| > `1.5 × max` (т. е. больше полупериода) | **Алиасинг**: следующее переключение LED произойдёт ДО прихода фронта от текущего; пойдут ложные значения с заниженной задержкой и/или массовый `lost`. Доверять такому результату нельзя |

Поэтому, если в финале вы видите большое количество `lost` или подозрительно низкие значения при, по ощущениям, медленном тракте, — **поднимите** `kLatencyMmaxExpectedMs` и перепрошейте.

### Можно ли менять только полупериод/таймаут вручную

Можно, но смысла мало — формулы простые и согласованные. Если хотите вручную: задайте свои значения и сохраняйте соотношения `таймаут < полупериод < ½ от среднего интервала между переключениями фронтов в тракте`.

## Что показывается на экране

Все экраны рассчитаны на 21 символ × 8 строк (SSD1306 128×64, шрифт по умолчанию).

### Глоссарий сокращений

| Сокращение | Полностью | Что значит |
|---|---|---|
| `R` | Red level | Среднее значение АЦП фотоприёмника, когда LED светит красным (0…1023) |
| `B` | Blue level | Среднее значение АЦП, когда LED светит синим (0…1023) |
| `sprd` / `+/-` | Spread | Разница `max − min` АЦП за фазу — грубая оценка шума/нестабильности освещения |
| `dRB` | Delta R↔B | Разница уровней `cB − cR` в кодах АЦП. Знак определяет `dirSign`. Чем больше по модулю — тем увереннее детектируется фронт |
| `mn` / `mx` | Min / Max | Минимальный и максимальный коды АЦП, наблюдавшиеся в текущей фазе |
| `n` | samples / count | Сколько отсчётов уже накоплено |
| `lost` | lost samples | Сколько переключений LED закончились **таймаутом** (фронт на датчике не пойман в окно ~200 мс) |
| `RB` | Red→Blue avg, ms | Средняя задержка перехода с красного на синий, миллисекунды |
| `BR` | Blue→Red avg, ms | Средняя задержка перехода с синего на красный, миллисекунды |
| `min/avg/max` | в финале/live | Минимум, среднее и максимум задержки по **всем** выборкам обоих направлений, в мс |

> Один код АЦП ≈ 5.0 В / 1024 ≈ **4.9 мВ** (опорное напряжение — `cfg::kAdcVrefVolts`).

### 1. Главное меню

```
KRAN  glass2glass
tap   = back
2tap  = CAL R/B
hold  = MEASURE

cal:  2ph x 5s
meas: 22s R<->B
max ~500ms
```

Значения времени и максимальной задержки **подтягиваются из `Config.h`** — если измените `kLatencyMaxExpectedMs`, экран и Serial обновятся автоматически.

| Строка | Что значит |
|---|---|
| `KRAN  glass2glass` | Заголовок прибора |
| `tap   = back` | Короткое одиночное нажатие → возврат в меню / выход из режима |
| `2tap  = CAL R/B` | Два коротких подряд → **явная калибровка** (2 фазы по `kCalibPhaseDurationMs`) |
| `hold  = MEASURE` | Удержание ≥ 3 с → авто‑прогрев и **измерение** длиной `kLatencySessionMs` |
| `cal:  2ph x Ns` | Реальная длительность одной фазы калибровки |
| `meas: Ns R<->B` | Реальная длительность сессии замера и режим стимула |
| `max ~Nms` | Верхняя граница измеримой задержки (`kLatencyMaxExpectedMs`) |

### 2. Экран фазы калибровки

```
CAL 1/2  RED
adc   812
mn 810  mx 814
sprd  4
n     320

tap = menu
```

| Поле | Пример | Что значит |
|---|---|---|
| `CAL 1/2  RED` | 1/2, RED | Номер фазы и подпись: 1=RED, 2=BLUE |
| `adc 812` | 812 | Текущее **среднее** АЦП за фазу |
| `mn 810  mx 814` | 810 / 814 | Минимум и максимум АЦП в этой фазе (разница = шум/мерцание) |
| `sprd 4` | 4 | `mx − mn`. Маленький spread (< 10) — хороший признак, освещение стабильно. Большой (> 50) — есть мерцание / плохой контакт / посторонняя засветка |
| `n 320` | 320 | Сколько отсчётов уже взято в этой фазе (опрос каждые `kCalibSamplePeriodMs = 15 мс`) |
| `tap = menu` | — | Короткое нажатие прервёт калибровку и вернёт в меню |

Что должно получиться: `RED` → один стабильный уровень АЦП, `BLUE` → существенно другой. Если уровни почти одинаковые — на следующем экране будет `FAIL: dRB low`.

### 3. Итог калибровки

```
CAL  RESULT

R    812 +/-4
B    210 +/-5
dRB  -602

status: OK
tap = menu
```

| Поле | Пример | Что значит |
|---|---|---|
| `R 812 +/-4` | 812, spread 4 | Уровень при красном. Не должен быть в районе 0 или 1023 (насыщение) |
| `B 210 +/-5` | 210, spread 5 | Уровень при синем |
| `dRB -602` | -602 | `cB − cR`. Знак: тут отрицательное — значит красный ярче синего (`dirSign = -1`). По модулю 602 — отличный спред, измерение будет очень надёжным |
| `status: OK` | — | Прошли обе проверки: спред ≥ 32, без клиппинга АЦП |
| либо `FAIL: <reason>` | `dRB low` / `ADC clip` | Причина отказа (см. таблицу 5 «Экран ABORT») |

### 4. Экран авто‑прогрева перед замером

```
WARMUP
phase 1/2
LED   RED

checking R/B
levels ...

tap = menu
```

| Поле | Пример | Что значит |
|---|---|---|
| `WARMUP` | — | Идёт быстрый авто‑прогрев перед каждым измерением (≈ 1 с суммарно: 2 фазы × `kWarmupPhaseDurationMs = 500 мс`) |
| `phase 1/2` | 1 | Номер фазы сканера 2 фаз |
| `LED   RED` | RED | Текущий цвет LED в этой фазе (RED / BLUE) |
| `checking R/B levels …` | — | Идёт измерение уровней и проверка пригодности |
| `tap = menu` | — | Можно прервать прогрев и вернуться в меню |

После прогрева автоматически переход либо в **измерение**, либо в **ABORT**.

### 5. Экран ABORT — нельзя измерять

```
ABORT  no measure
reason: dRB low


R    512
B    528
dRB  16

tap = menu
```

| Поле | Пример | Что значит |
|---|---|---|
| `ABORT  no measure` | — | Прибор отказался начинать замер по результатам прогрева |
| `reason: <код>` | `dRB low` | Причина (см. таблицу ниже) |
| `R / B / dRB` | значения АЦП после прогрева | Диагностика — что именно увидел прибор |
| `tap = menu` | — | Возврат в меню |

Причины:

| reason | Что произошло | Что делать |
|---|---|---|
| `dRB low` | `|cR − cB| < 32` — цвета почти неразличимы | Подобрать резисторы R/B, чтобы яркости отличались сильнее; убедиться, что в кадре виден сам LED; уменьшить постороннюю засветку (фон «топит» оба уровня) |
| `ADC clip` | `cR` или `cB` ≤ 4 или ≥ 1019 — АЦП в насыщении | Уменьшить ток LED или подкрутить подтяжку фотодиода; снизить яркость монитора |
| `no data` | сканер не успел набрать выборки | Не должно случаться в норме; проверить опрос АЦП |

### 6. Live‑экран во время измерения

```
LAT 4.3/22.5
n 28  lost 1
min  12.4 ms
avg  42.7 ms
max  78.1 ms

RB 41.5  BR 43.9
tap = exit
```

| Поле | Пример | Что значит |
|---|---|---|
| `LAT 4.3/22.5` | 4.3 / 22.5 | Прошло секунд / всего секунд сессии (значение справа = `kLatencySessionMs / 1000`) |
| `n 28` | 28 | Накоплено валидных выборок (обоих направлений суммарно) |
| `lost 1` | 1 | Потеряно выборок (таймаут датчика > 200 мс — фронт не пойман) |
| `min  12.4 ms` | 12.4 мс | **Минимальная** задержка по всем выборкам обоих направлений |
| `avg  42.7 ms` | 42.7 мс | **Среднее** по всем выборкам |
| `max  78.1 ms` | 78.1 мс | **Максимум** (обычно ограничен размером кадра камеры и частотой обновления монитора) |
| `RB 41.5  BR 43.9` | 41.5 / 43.9 | Средние задержки отдельно по направлению `Red→Blue` и `Blue→Red` |
| `tap = exit` | — | Короткое нажатие прервёт замер и вернёт в меню |

Обновление экрана — ~4 раза в секунду (`kLatencyUiPeriodMs = 250 мс`). Если `lost` растёт быстро (десятки за пару секунд) — есть проблема: либо тракт уронил поток, либо камера/монитор не успевают за полупериодом стимула (250 мс).

### 7. Финальный экран `GLASS→GLASS`

```
GLASS->GLASS  ms
min  12.40
avg  42.70
max  78.10
RB   41.50
BR   43.10
n=240  lost=3
tap = menu
```

| Поле | Пример | Что значит |
|---|---|---|
| `GLASS->GLASS  ms` | — | Заголовок: все значения ниже — в **миллисекундах** |
| `min 12.40` | 12.40 мс | Минимальная задержка за сессию. Это «лучший случай», обычно соответствует моменту, когда переключение LED совпало с началом нового кадра камеры |
| `avg 42.70` | 42.70 мс | Среднее — основная характеристика, которую обычно записывают в протокол |
| `max 78.10` | 78.10 мс | Максимум — «худший случай», даёт представление о джиттере. Если `max − min` > 2/FPS камеры — нормально (кадровая дискретизация). Гораздо больше — есть джиттер в тракте (буферизация декодера, потери пакетов, vsync) |
| `RB 41.50` | 41.50 мс | Среднее по направлению `Red→Blue` |
| `BR 43.10` | 43.10 мс | Среднее по направлению `Blue→Red`. Разница 1–10 мс между `RB` и `BR` — норма (асимметрия Bayer/ISP/панели) |
| `n=240` | 240 | Сколько валидных выборок легло в статистику. Ожидаемое число выборок ≈ `kLatencySessionMs / kLatencyBlinkHalfPeriodMs`. При значениях по умолчанию (`max=500 мс`) это ~30 |
| `lost=3` | 3 | Сколько переключений завершились таймаутом. Доля `lost / (n + lost) < 5 %` — хорошо |
| `tap = menu` | — | Возврат в меню. Результат не сохраняется в EEPROM — только в RAM до перезагрузки/нового замера |

### Краткая шпаргалка «как читать результат»

| Что увидели | Как трактовать |
|---|---|
| `avg ≈ min ≈ max` | Тракт стабильный, без джиттера (редкость для IP/Wi‑Fi) |
| `max − min` ≈ 1–2 / FPS камеры | Нормальная кадровая дискретизация |
| `max ≫ avg` (в разы) | Буферизация в декодере / повторы пакетов в Wi‑Fi |
| `RB` сильно ≠ `BR` (> 15 мс) | Сильная асимметрия обработки цвета или панели; повторите замер с обмененными местами цветами или другим монитором |
| `lost` > 10 % | Слишком короткий полупериод для тракта, либо потери в линке. Увеличить `kLatencyBlinkHalfPeriodMs` |

## Хранение калибровки

Только **в RAM** (структура `app::CalibData`). При перезагрузке прибора калибровка теряется — это упрощает прошивку и гарантирует, что значения порогов соответствуют текущим условиям съёмки. Перед каждым измерением автоматически выполняется **короткий авто‑прогрев** (2 фазы по `cfg::kWarmupPhaseDurationMs`), который пересчитывает `cR / cB / mid` и принимает решение о пригодности.

## Что измеряется и что нет

Прибор измеряет **полную end‑to‑end задержку** видеотракта: оптика камеры → сенсор → ISP → кодировщик → транспорт → декодер → композитор → панель монитора → пиксель → фотодиод. Тракт может быть **любым** — аналоговым, IP, беспроводным.

В измерение **входит** время отклика ЖК панели, **не входит** только время самого МК на подачу команды (десятки микросекунд) — пренебрежимо мало по сравнению с типичными десятками миллисекунд тракта.

## Методика для повторяемых измерений

1. Прогреть камеру и монитор не менее 10 минут.
2. На камере зафиксировать экспозицию/усиление/баланс белого (например, в OpenIPC `majestic.yaml` — `exposure: manual`), отключить «динамические» обработки (HDR, шумодав, если возможно).
3. На мониторе зафиксировать яркость, отключить «динамический контраст» и «overdrive» (или зафиксировать профиль).
4. Прижать фотоприёмник к экрану монитора в бленде (без посторонней засветки), LED поместить в визирный кожух перед камерой (без бликов).
5. Сделать `2tap` — явную калибровку, убедиться, что `status: OK`.
6. Сделать долгое удержание — авто‑прогрев и замер. Повторить 5–10 раз.
7. Фиксировать в протоколе: `min / avg / max`, `RB`, `BR`, `n`, `lost`, конфигурацию тракта (кодек, разрешение, FPS, битрейт, транспорт, частота обновления монитора).
